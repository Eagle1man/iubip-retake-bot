# DECISIONS — решения по MVP «Запись на пересдачу»

Каждое решение: что решили, почему, и что было отклонено.
План исполнителя: `D:\itотдел\docs\plan-iubip-retake-bot-mvp.md`, заявка T-1074.

## 1. Окружение разработки: WSL2, а не Docker

Postgres 16 и Redis 7 подняты нативно в WSL2 и проброшены на
`localhost:5432` / `localhost:6379`. Скрипты: `scripts/wsl-setup.sh`,
`scripts/wsl-grant.sh`.

**Почему:** на машине разработчика нет Docker Desktop, а в WSL-демоне
bridge-сеть не работает — `docker compose up` здесь физически не прогнать.
Docker-часть (`Dockerfile`, `docker-compose.yml`, `Caddyfile`) написана по
плану §15, но **на этой машине не проверялась** — это открытый риск, он же
в артефакте заявки.

**Отклонено:** Testcontainers (требует Docker API), compose для локальной
разработки (нет демона).

## 2. E2E: одна тестовая БД, файлы последовательно

`test/setup/global.ts` создаёт `iubip_retake_test` и накатывает миграции,
`fileParallelism: false` — все тестовые файлы делят одну БД.

**Почему:** Prisma-тесты с `resetDb` в `beforeAll` при параллельных файлах
стирают данные друг друга. Последовательность стоит ~40 с на весь набор и
делает падения воспроизводимыми.

**Отклонено:** БД на тест на файл (удорожает каждый прогон) и параллелизм
(флейки).

В compose для E2E есть отдельный сервис `e2e` (профиль `test`) — он гоняет
тот же `vitest.e2e.config.ts` против БД compose. Локально: `npm run test:e2e`.

## 3. `prisma` и `tsx` — в `dependencies`

Контейнер запускает `prisma migrate deploy` и `prisma db seed` перед стартом
(план §15.1), поэтому CLI мигратора и `tsx` (сид написан на TypeScript)
должны жить в рантайме.

**Отклонено:** собирать `prisma/seed.ts` отдельным tsc-проходом (`rootDir=src`
в конфиге — пришлось бы городить второй tsconfig ради одной команды).

Заодно удалён `@fastify/static` — зависел, но не использовался нигде.

## 4. Порты БД и Redis в compose не публикуются

**Почему:** на машине разработчика уже живут локальные Postgres/Redis на тех
же 5432/6379. Публикация портов сломала бы `docker compose up` конфликтом
привязки без единой пользы — compose-сервисы общаются по внутренней сети.

## 5. Подпись вебхука MAX: сравнение с секретом как есть

`verifyWebhook` сравнивает заголовок `x-max-signature` с `MAX_WEBHOOK_SECRET`
через `timingSafeEqual`.

**Почему:** реальный формат подписи MAX не документирован в ТЗ и у нас нет
боевого токена, чтобы его вывести.

**Риск:** при боевом включении функция проверки потребует замены под фактический
алгоритм MAX — иначе вебхук будет отклоняться. Помечено в README.

## 6. jobId уведомления: уникальный на событие, дефис вместо двоеточия

`QueueNotificationSink` строит `notify-<kind>-<scope>-<userId>-<счётчик>`.

**Про двоеточие:** BullMQ 5 отклоняет `:` в custom jobId («Custom Id cannot
contain :») — с `notify:` уведомления не ставились бы в очередь вообще.
Поймано тестом `test/integration/notifications.throttle.test.ts`, а не
анализом кода.

**Про уникальность:** id был детерминированным (`kind + slotId + userId`), и
это ломало доставку: BullMQ не добавляет дубль jobId, а завершённые джобы
лежат в наборе completed. Поэтому повторное событие — вторая смена аудитории,
повторная отметка оплаты после сброса стенда — **молча не отправлялось
вовсе**: получатель просто не получал уведомление. Найдено гейтом 22.10.2026
на живом прогоне демо.

**Как теперь:** уникальный id (счётчик `notify:seq` в Redis), а идемпотентность
обеспечивает домен — уведомление уходит только при фактическом изменении
(повторная отметка той же оплаты и повторная смена на ту же аудиторию
уведомлений не порождают). Закреплено тестами `notifications.repeat.test.ts`,
`bookings.test.ts`, `slots.test.ts`.

## 7. Пустой `body` с `content-type: application/json` → `{}`

**Почему:** Fastify по умолчанию отвечает на такое 400, хотя POST-эндпоинты
вроде `/:id/cancel` тела не требуют. Клиент, отправивший пустой POST, получал
бы неверный статус. Некорректный JSON остаётся 400.

## 8. `kind` уведомления пробрасывается в клиент MAX

`sendMessage(userId, text, keyboard?, kind?)`; mock-клиент пишет
`kind ?? "outgoing"`.

**Почему:** в mock-режиме журнал иначе состоял бы только из `outgoing` и не
отвечал бы на вопрос «по какому событию отправлено» — а критерий §11.3 шаг 8
требует `kind='slot_cancelled'` у студента. Боевой клиент `kind` игнорирует.

**Отклонено:** дублировать строку в `NotificationLog` ещё и воркером — в
эмуляторе каждое уведомление показывалось бы дважды.

## 9. `expectedCapacity` не блокирует запись

Правило из §13.13: размер аудитории справочный. О превышении пишет
уведомление дирекции (`maybeAlertOverflow`), но запись создаётся.
Ошибку отправки уведомления домен глотает — тест
«§13.13: сбой уведомления не должен ронять запись».

## 10. Миграции: частичный индекс дописывается вручную

Prisma не умеет частичные индексы, а защита от второй активной записи на
дисциплину — это именно он
(`CREATE UNIQUE INDEX ... WHERE status IN ('submitted','paid')`).

- `scripts/migrations-fix.mjs` — дописывает индекс **в ту миграцию, где
  создаётся таблица Booking** (иначе при применении с нуля индекс упадёт с
  «relation Booking does not exist»); защищён от двойного добавления
  чтением файла;
- `scripts/apply-migration.mjs` — **только для этой машины**: команда
  `prisma migrate deploy` блокируется правилом разрешений shell агента, а
  скрипт делает то же самое (выполняет SQL и пишет строку в
  `_prisma_migrations` с контрольной суммой sha256). На машине без таких
  правил достаточно `npm run db:migrate`. **В контейнере этот скрипт не
  нужен**: `prisma migrate deploy` применяет файл миграции целиком, вместе
  с дописанным частичным индексом.

## 11. Токен deep link не захардкожен в README

Seed печатает `DEEP_LINK=rt_<disciplineId>_<slotId>` с реально созданными
`cuid` — токен читается из логов (`docker compose logs app` / вывод seed).

**Отклонено:** фиксированный id **дисциплины** — она остаётся `cuid`, поэтому
токен нельзя зашить в README. А вот id демо-**сессии** теперь фиксированный
(`seed-slot-math-1`, см. §16): он не входит в разбор токена как отдельная
часть, поэтому `rt_<cuid>_seed-slot-math-1` парсится как прежде.

## 12. Пороги покрытия

`vitest.config.ts`: 80% строк/функций/утверждений и 75% веток по
`src/domain/**`. Фактический результат — 92.6% строк, 94.7% функций,
84.4% веток (см. README, «Тесты»).

## 13. Публикация

`docker compose --profile prod up -d` поднимает Caddy перед приложением.
**Публикацию на production делает человек** — агент деплой не выполняет.

## 14. `.env` читает само приложение

`src/infra/env-file.ts` поднимает `.env` из `src/config.ts`; тот же код
используют `test/setup/env.ts` и `test/setup/global.ts` — парсер один.

**Почему:** `tsx`, `node` и vitest файл окружения сами не читают. Без этого
`npm run dev` падал на `DATABASE_URL: Required`, хотя `.env` лежит рядом
(поймано при проверке README, а не при написании кода).

**Отклонено:** зависимость `dotenv` (лишняя зависимость ради 20 строк) и
`node --env-file` (требует Node ≥20.12, а в `engines` — `>=20`).

## 15. Порт локального запуска

По умолчанию 3000; на машине разработчика этот порт занят другим сервисом,
поэтому локальная проверка шла с `PORT=3100`. В README — явная подсказка.
В compose порт тоже настраивается: `APP_PORT=3100 docker compose up`.

## 16. Сид: фиксированный id сессии

Слот демо-сессии имеет фиксированный id (`seed-slot-math-1`), и сид приводит
его к исходному состоянию (аудитория `А-204`, статус `open`, свежие даты).

**Почему:** раньше слот искался по `room="А-204"`. Демо меняет аудиторию и
отменяет сессию, после чего повторный сид не находил свой слот, создавал
второй, а запись уходила в `create` и падала с `P2002` по частичному индексу
`booking_active_one_per_discipline`. Поймано гейтом 22.10.2026: «не более трёх
падений подряд» — на самом деле падал каждый второй запуск.

**Как проверяется:** `test/integration/seed.idempotent.test.ts` воспроизводит
сценарий (сид → порча стенда → сид) и требует, чтобы слот остался один, а
запись — одна и в статусе `submitted`.

## 17. Демо проверяется на живом сервере, а не только в тестах

`scripts/demo12.mjs` гоняет сценарий §12 по HTTP против поднятого приложения
(19 проверок). Тот же сценарий в e2e идёт через инжект и не воспроизводит
маршрутизацию HTTP и то, что видит UI.

**Почему:** дефекты `keyboard` в истории и «повторное событие не доходит»
были зелёными в 113 тестах и находились только на живом прогоне.

**Правило скрипта:** уведомления ищутся только среди сообщений, пришедших
после старта прогона, и берётся последнее совпадение — иначе сообщение
прошлого прогона засчитывается как успех текущего (на этом гейт и поймал
ложные OK).

## 18. Ловушки миграций и очереди

**P3008/P3009.** Если файл миграции правили после её применения, Prisma
откажется дальше применять миграции («modified after applied» / «found
migrations, but not applied»). Поэтому `scripts/migrations-fix.mjs` нужно
запускать **до** первого применения миграции на целевой БД. Если миграция уже
применена, а файл потом изменился — путь один: `npm run db:reset` (пересоздать
схему) либо ручная правка `_prisma_migrations`.

**Индекс идёт в свою миграцию.** `migrations-fix.mjs` ищет миграцию с
`CREATE TABLE "Booking"` и дописывает индекс туда. Дописывание в «последнюю по
дате» миграцию ломает применение с нуля: индекс появится раньше таблицы.

**Счётчик `notify:seq` в Redis** растёт монотонно и никогда не уменьшается —
это нормально для `INCR` (64-бит), переполнения не будет. Дубликатов
идентификаторов он не создаёт.

**Троттлинг и живые Redis.** Тест троттлинга оставляет в общей очереди
задержанные джобы; после него очередь обнуляется (`obliterate`), иначе эти
джобы уедут в следующий запуск приложения и человек увидит чужие сообщения.
